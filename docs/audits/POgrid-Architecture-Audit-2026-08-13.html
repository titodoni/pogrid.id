The 5 most important findings

Finding 1 — Email verification is a dead gate: the verified middleware protecting every office route is a no-op P0

Evidence: app/Models/User.php:11 — class User extends Authenticatable does not implement MustVerifyEmail. app/Http/Middleware/EnsureEmailIsVerified.php:21-23 checks $user instanceof MustVerifyEmail, which is always false, so every request passes. The middleware also returns early in the testing environment (:17-19), making the gap undetectable by the test suite. All office routes sit behind auth, verified (routes/web.php:59-101).

Impact: The email-verification infrastructure (controller, signed routes, notifications) is decorative. Any registered account reaches the office dashboard regardless of verification. A security control that looks present in the routing table but never fires is worse than none — it suppresses scrutiny.

Recommendation: Add MustVerifyEmail to User, remove the testing-env bypass, add a feature test proving unverified users are redirected.

Finding 2 — Authorization is opt-in per controller method and several mutating endpoints have none; credentials leak into alert messages and a plaintext email log P0

Evidence: No role middleware exists (bootstrap/app.php:28-30 registers only verified). Authorization is a scattered set of Gate::authorize() calls; any method missing a call is open to every authenticated user:

  • PpicDashboardController::updatePo (:358) and ::updateItemPriority (:381) — no authz: any floor worker can rewrite PO deadlines, urgency and item priority.
  • PinResetController::approvePinReset (:55) — no authz: any authenticated user can approve PIN resets; the new PIN is stored plaintext in the alert message (PinResetController.php:83: "PIN Reset Approved for {name}. New PIN: {pin}"), persisting credentials in the alerts table.
  • OwnerDashboardController::changePassword (:602), ::billing (:838), ::reworkLogbook (:623), ::listStageTemplates (:525) — no authz calls (read paths mitigated only by tenant scoping).
  • app/Providers/AppServiceProvider.php:133-163 — a MessageSending listener appends every outgoing email body (temporary passwords, reset links) to logs/verification-emails.log in plaintext, outside storage/.

Impact: Post-login privilege escalation paths for floor workers; live credentials at rest in two locations. Guard B's "office roles blocked from PIN login" is undermined once any session exists.

Recommendation: Introduce a role middleware (e.g. role:office) on the office route group and per-route gates on PPIC mutations; never persist PINs in alert rows (flash once, done); remove the email-body file logger.

Finding 3 — Two god files concentrate the majority of change risk: WorkerDashboardController.php (1,946 LOC) and Pages/Owner/Dashboard.tsx (4,203 LOC) P1

Evidence: Three controllers hold 61% of all backend LOC (Worker 1,946 + Owner 878 + PPIC 402 = 3,226 of 6,171). WorkerDashboardController::getTelemetryData (:451-941) is a ~490-line KPI method; ::updateProgress (:1178-1324) performs five model writes (ItemProgress, Item, DeliveryOrder, DoItem, Alert) with no DB::transaction. Owner/Dashboard.tsx contains 71 useState calls, 46 any annotations, 220 inline-style blocks, and mixes a search engine (:557-602), ETA estimation (calculateDynamicETA :359-417), a piece-location algorithm (:280-357), user CRUD, stage-template CRUD (including the app's only raw fetch('/stage-templates') at :1112/:4080), Echo presence handling, and ~2,700 lines of JSX.

Impact: Nearly every dashboard feature touches the same two files: merge conflicts, wide regression blast radius, slow reviews, high onboarding cost. This is the primary scaling bottleneck for the team.

Recommendation: Extract analytics into plain PHP query/service classes and page tabs into feature components. No new framework or pattern is required.

Finding 4 — Core business rules exist in 2–4 divergent copies across PHP and JS P1

Evidence:

  • STAGE_ROLE_MAP: WorkerDashboardController.php:29; resources/js/Utils/permissions.ts:50-62; and a third inline redefinition in Worker/Dashboard.tsx:99-224 that shadows its own imports from permissions.ts — the local copy has already diverged (missing STAFF in officeRoles, :129).
  • Deadline-risk rule: cron requires daysRemaining <= 3 && progress < 70 (app/Console/Commands/EvaluateTimelines.php:56); the Owner Dashboard renders risk pills at diffDays <= 3 only (Owner/Dashboard.tsx:846 and :2639) — the UI shows risks the backend never raises, and vice versa.
  • Status vocabulary drift: ItemProgressObserver.php:88 sets items to IN_PRODUCTION, but PoCompletionChecker.php:27 only recognizes IN_PROGRESS — a PO never transitions PENDING → IN_PROGRESS through the completion checker (only → COMPLETED). AGENTS.md documents yet another lifecycle (PENDING → IN_PROGRESS → COMPLETED).
  • Finance-complete rule copy-pasted 4× in Worker/Dashboard.tsx (:107, :196, :266, :331) plus permissions.ts:203. PO progress computed client-side as an unweighted average (Owner/Dashboard.tsx:2467-2469) does not match the server-side weighted formula (ItemProgressObserver.php:63-67).

Impact: UI and backend disagree about ground truth; every rule change is multi-file surgery and copies are measurably drifting apart.

Recommendation: Server becomes the single source of truth; ship the stage-role map and status vocabulary to the client as Inertia props or a config endpoint. Delete the JS copies.

Finding 5 — Known runtime crashes shipped on the floor-worker UI because TypeScript checking is not enforced P0

Evidence:

  • Worker/Dashboard.tsx:1858 passes translations={translations} to ItemCard, but no translations binding exists in page scope (all occurrences: :85, :93, :95, :122, :1858 — none define it) → ReferenceError whenever items render.
  • Worker/Login.tsx:496 calls setSelectedWorker(null); only setSelectedWorkerId exists (:60) → ReferenceError on a successful PIN-reset request.
  • Worker/Dashboard.tsx:915 ships malformed JSX (< label ... with a stray <) rendering literal text on the Finance panel.
  • A tsconfig.json now exists (added 2026-08-12) but with "strict": false, and package.json has no typecheck script — Vite compiles TS without type-checking. All three bugs are statically detectable.

Impact: The users least tolerant of UI failure — floor workers on shared devices — are the ones hitting crashes on core flows.

Recommendation: Fix the three bugs immediately; add tsc --noEmit to CI and to the build; ratchet strict up over time.

Assessment of major choices

  1. Laravel 11 + Inertia + React — One team shipping a server-driven app with rich client interactivity, without maintaining an API. Fits the product. Plumbing is idiomatic (Inertia share, HandleInertiaRequests, Vite plugin). No evidence justifies an API/SPA split or microservices at this size.
  2. Custom dual auth instead of Laravel guards — Guard B is a controller-level PIN check on the shared users table, not a real guard. It works, but bypasses the framework's guard system; the visible cost is tenant/role context being re-derived manually in ~8 controller methods (WorkerDashboardController.php:72-78, 185-191, 279-285, 428-436, …). A project-specific decision with contained but real complexity cost.
  3. Eloquent observers as the business-logic home — Documented doctrine ("business logic lives in observers, NOT controllers" — AGENTS.md). Reality: observers own recalculation/cascades; controllers still own write orchestration, stage gates, thresholds, and KPI math. Workable, currently strained (see §5).
  4. Database queue + 1-minute cron — routes/console.php:11-12 schedules queue:work --stop-when-empty and pogrid:evaluate-timelines with withoutOverlapping. Correct fit for daemon-less shared hosting. Do not add Redis/Horizon.
  5. DomPDF + OpenSpout — Both genuinely used (app/Services/ExportService.php:5-8). Justified.
  6. Pusher — Real-time dashboard refresh. Fits. The 3-broadcasts-per-progress-write amplification (§13) is a usage issue, not a stack issue.
  7. Tailwind v4 + Astryx — Tailwind usage is idiomatic. @astryxdesign/core is imported (app.tsx:1-2); @astryxdesign/cli and @astryxdesign/theme-neutral have zero references — dead devDependencies.
  8. TypeScript present but unenforced — tsconfig.json exists with strict:false; no typecheck script; Vite does not type-check. The one case where using an already-adopted tool as intended would have prevented shipped production bugs (Finding 5).

Stack as a system: lean (4 production Composer packages beyond the framework, 5 production npm packages), coherent, no exotic infrastructure. The stack is right; discipline inside it is the gap. No technology replacement is recommended.

3.Architecture Assessment

Actual architectural style: server-rendered monolith with Inertia.js (no API layer), Eloquent-observer-driven domain logic, cron-based async work (queue + timeline evaluation), and Pusher broadcast fan-out. Two entry surfaces — office (/login, /dashboard) and floor (/c/{slug}) — served by one application.

Actual request/data flow (representative: worker progress update)

POST /c/{slug}/progress/{id}/update → web middleware group (RedirectToAppDomain, HandleInertiaRequests, SetTenant) → auth → WorkerDashboardController::updateProgress → inline $request->validate() (no FormRequests exist anywhere) → manual tenant re-resolution (TenantManager::bypass → Tenant::where(slug) → enableScope → setTenantId — repeated ~8×) → validateStageAccess() (STAGE_ROLE_MAP gate, in-controller) → write ItemProgress → ItemProgressObserver::saved (DB::transaction + lockForUpdate) → recalc item % → update Item → ItemObserver (activity log) + DataSyncObserver → broadcast → PoCompletionChecker → update Po → another broadcast → controller also writes DeliveryOrder / DoItem / Alert (untransacted relative to the observer's transaction) → Inertia redirect with flash

Responsibility separation

  • Cohesion: poor in controllers (analytics + writes + exports + tenant plumbing in one class); good in models (thin, relations + accessors); good in ExportService / ActivityLogger (single-purpose).
  • Coupling: high between controllers and the static TenantManager; observers coupled to ActivityLogger, PoCompletionChecker, and broadcasting.
  • Dependency direction: mostly sane (controllers → models → observers → services). The real inversion is client-side: the frontend re-implements server rules (Utils/permissions.ts), so the browser depends on server policy it duplicates rather than consumes.
  • Business logic placement: split three ways — observers (progress recalc, cascades), controllers (stage gate, thresholds like 33/66 at WorkerDashboardController.php:1219, KPI math), and JS (Finding 4). The documented doctrine is only half-true.
  • Shared/global state: TenantManager is a static mutable singleton (app/Services/TenantManager.php:7-9). Safe only because PHP-FPM is per-request and cron uses --stop-when-empty; it would be a live bug under Octane or a queue daemon. TenantScope fails open — when no tenant id is set, queries run unscoped (app/Models/Scopes/TenantScope.php:12-22).
  • Domain/module boundaries: none beyond controllers — acceptable at this size. Cross-layer leakage exists: Item::getItemNameAttribute rewrites display names on read (app/Models/Item.php:78-81); alert message strings are used as data keys (§9).
  • Circular dependencies: none detected.

Where business logic lives

  • Observers (recalc & cascades): ItemObserver::created (:21-39) spawns one ItemProgress per required stage. ItemProgressObserver::saved (:34-110) does the weighted recalc inside DB::transaction + lockForUpdate (:37), updates item status, cascades to the PO. DoItemObserver::saved recomputes delivery status. This chain is the best-structured part of the backend.
  • Controllers (everything else): stage-gate rules (validateStageAccess :1805-1945), KPI/analytics engine (getTelemetryData :451-941 — OTDR, delays, trends, bottleneck, client health), purchasing thresholds (:1219), finance transitions, rework orchestration.
  • Client JS: stage-role map, deadline-risk rule, finance rule, progress aggregation — all duplicated (Finding 4).

Specific backend findings

  • Services are meaningful, not CRUD wrappers: TenantManager, ActivityLogger, PoCompletionChecker, ExportService each have a real responsibility. No service-layer bloat.
  • Duplicated business rules: cancel rule progress > 0 inline at OwnerDashboardController.php:500 duplicating ItemPolicy::cancel (ItemPolicy.php:20-22); purchasing thresholds 33/66 at WorkerDashboardController.php:1219,1389 and again in BackfillItemStages.php:59,70; tenant-resolution boilerplate copy-pasted in ~8 methods; $stageGroups verbatim twice in PpicDashboardController.php:125-134 and :318-327.
  • Transactions: createPo (OwnerDashboardController.php:228-252) is the only transacted controller path. updateProgress, logQcRework (:1523-1560), and RegistrationController::register (:53-96, creates Tenant+User) are multi-write and un-transacted — partial states are persistable.
  • Registration slug bug: slug validated unique:tenants,slug on raw input (RegistrationController.php:30) then lowercased at :44 → ABC vs existing abc passes validation, then violates the DB unique index → 500. Username-collision while loop (:81-83) is a race condition.
  • Authorization layer: wrong layer, patchy coverage (Finding 2). AlertPolicy.php and TenantPolicy.php are 0-byte files. Gates string-match on role/post names (AppServiceProvider.php:35-111) and are asymmetric — manage-company-settings denies only Manager+Sales (:40-56), so floor roles technically pass it.
  • Broadcast amplification: one progress write can emit up to 3 Pusher events (ItemProgress save → Item update → PO update, each firing DataSyncObserver). Cost and client noise.
  • Cascade note: ItemProgressObserver::saved also fires on progress-row creation — creating an item with N stages triggers N full recalcs (each taking a row lock and reloading all stages). Correct results, wasteful execution.
  • Cron logic: EvaluateTimelines (98 LOC) bypasses scope globally (:22), loops all tenants and all active items; alert dedup keys on the full message string containing the item name (:44-52, :57-65) — renaming an item duplicates its alerts. Magic values: 3 days, 70% (:56), 24h escalation (:81).
  • Job: GenerateSunkCostInvoiceJob — hardcoded pricing heuristic max(150000, qty * 150000) (:43), uniqid() invoice numbers (:41), and a finally that calls enableScope() (:55) even when bypass was set by the caller — a state-restore bug in nested-bypass contexts.

Integrity risks (ranked)

  1. Missing unique constraints with race windows P1 — pos.po_number uniqueness enforced only by form validation (OwnerDashboardController.php:192); delivery_orders.do_number and invoices.invoice_number have no DB backstop. Concurrent creates can duplicate business identifiers.
  2. Alert dedup without a unique key P1 — EvaluateTimelines.php:44-65 uses updateOrCreate keyed on tenant+item+severity+message text; concurrent cron runs can duplicate rows, and renames fork the key.
  3. Missing indexes on proven hot paths P2 — alerts(tenant_id,is_resolved) (filtered at WorkerDashboardController.php:117,506,594,603,1474 and EvaluateTimelines.php:82-87); do_items FK columns (summed per item at DoItemObserver.php:20, PoCompletionChecker.php:53, Item.php:55); users.tenant_id/role_id/post_id (worker lists, role joins). PostgreSQL does not auto-index FK columns.
  4. Unindexable LIKE scans P2 — stage-name queries use leading wildcards (stage_name LIKE '%Design%'-style at WorkerDashboardController.php:211-263, 1885, 1899) inside whereHas per dashboard load. Root cause: stages are free-text strings, not a relation.
  5. Redundant indexes on a hot write table P3 — items carries 6 indexes; single-column status/invoice_status/payment_status indexes are subsumed by the two composites. Write amplification on every observer recalc.
  6. Hard delete on pos with DB cascade, audit-link erosion P2 — Po::delete() hard-deletes and DB-cascades into items/progress; activity_logs.item_id/project_id use nullOnDelete, so audit rows silently lose linkage when a PO is removed.
  7. Status columns are unconstrained strings P2 — every lifecycle column (pos.status, items.status, invoice_status, …) is a free-text string; the IN_PRODUCTION vs IN_PROGRESS drift (Finding 4c) is exactly the failure mode a DB/PHP enum would prevent. roles.level shows the pattern is known.
  8. Denormalized is_urgent P3 — exists on both pos (2026_06_28) and items (2026_07_17) with no sync rule; drift risk.

Data types: money is decimal(15,2) everywhere (no floats) — correct. JSON used for required_stages, workflow_settings, stages, metadata — portable across SQLite/PostgreSQL. No raw SQL detected; SQLite/PostgreSQL portability is otherwise fine.

Tenant-boundary risks (architectural, no exploit demonstrated)

  1. Fail-open scope P1 — every controller/command/job must remember to set tenant context; a single missed path reads cross-tenant. The system relies on convention, not construction. Fail-closed (throw when no tenant is set outside an explicit bypass) would remove the class of bug.
  2. do_items is the only business table outside the tenant scope P2 — no tenant_id column, no trait (app/Models/DoItem.php:9-12). Safe today only because all access arrives via scoped parents and item PKs are globally unique. Zero defense-in-depth; the first direct DoItem::find($id) in a new feature is a cross-tenant read.
  3. Global unique username/email P2 — by design (login resolves users across tenants, AuthController.php:29-31), but it makes cross-tenant account enumeration possible by probing duplicate usernames, and prevents per-tenant username reuse. Accepted tradeoff, worth recording as a decision.
  4. users.tenant_id nullable P3 — a null-tenant user passes BelongsToTenant creation rules and lives outside every scope; verify no registration path can produce one unintentionally.

Positive evidence: tests/Feature/TenantScopeAuditTest.php (300 LOC) explicitly attacks cross-tenant reads/writes, WebSocket channels, and dashboard access — tenant isolation is the best-tested boundary in the system.

17.Architectural Efficiency

Question: is this codebase doing too much, too little, or about the right amount of architecture?

Verdict: appropriately engineered in shape; under-engineered in enforcement.

  • Abstraction layers: Routes → Controller → Observer → Model, plus 4 services. That is the right number for this product. No repository/event-sourcing/DDD cargo cult anywhere.
  • Dependencies: lean on both manifests (§11). Nothing to unwind.
  • Concepts a developer must learn: dual auth-by-convention, static TenantManager + scope lifecycle, observer cascade chain, stage-role map, dual-language mechanism, theme system. ≈6 project-specific concepts — moderate, but two of them (auth-by-convention, static tenant state) are concepts created by under-using the framework, not by product complexity.

  • Framework functionality bypassed: FormRequests, role middleware, MustVerifyEmail, route model binding, Ziggy — all omitted, each omission now carrying interest.
  • Cost of an ordinary feature: currently: add controller method in a god file + add gate call (remember!) + add JS copy of any rule + add translations in 2-3 places + add route + hardcode URL on client. That is 5-6 touchpoints where 2-3 would do — the clearest quantitative signal of under-enforcement, not over-design.

20.Recommendation

Keep — working well, do not change

  • The monolith + Inertia architecture. No API split, no microservices — right-sized for team and product.
  • The stack itself. Laravel 11, React 18, Tailwind v4, SQLite→PostgreSQL, database queue via cron, Pusher. Lean and coherent (§2, §11).
  • The observer cascade concept. ItemProgress→Item→PO recalculation with transaction + row lock (ItemProgressObserver.php:34-110) is the best-engineered part of the system. Keep the pattern; fix its status vocabulary.
  • ExportService, ActivityLogger, AppShell — single-purpose, shared, healthy.
  • The test suite's core — tenant-isolation attack tests and stage-flow coverage are genuinely good (§12).
  • Broadcast channel design — tenant-checked, role-split, tested (§8).
  • Design-token theme system + Utils/date.ts — good ideas; just centralize the copies.

Improve — same architecture, better discipline

  • Close the P0 security gaps (email verification contract, role middleware, credential logging, throttles).
  • Enforce the TypeScript already in the repo: tsc --noEmit in CI, strictness ratchet.
  • Wrap multi-write controller paths in DB::transaction.
  • One hardening migration: per-tenant unique constraints, hot-path indexes, drop redundant item indexes, scope do_items.
  • Make the tenant scope fail-closed; keep bypass() explicit.
  • Replace message-string keys with structured alert columns.
  • Server-own the stage-role map and status vocabulary; client consumes as props/config.
  • Factories for Tenant/Po/Item/ItemProgress; Mail/Notification fakes; tests for PIN-reset, forgot-password, batch actions.
  • One deploy path; CI stops uploading public/hot; e2e wired in.
  • Refresh AGENTS.md; consolidate root docs; delete dead code/deps.

Change — structural, but incremental (no rewrite)

  • Authorization architecture: from opt-in per-method gates to enforced route-group middleware + policies as the second layer. This is a structural change in how safety is guaranteed, not a rewrite.
  • Decompose the two god controllers into feature services (plain PHP classes: TelemetryService, ProgressService, StageGate) and the god page into tab-level feature components. Controllers become thin; the frontend gets feature boundaries. Trigger: do it before the next 5 dashboard features land.
  • Unify the status lifecycle vocabulary (one enum-like constant set shared by observer, checker, and client) — currently three documents disagree about what an in-progress item is called.

Explicitly not recommended: microservices, repository pattern, an API layer, event sourcing, Redis/Horizon, a state-management library, or an i18n framework. Nothing in the evidence justifies them at this size.

22.CTO Executive Summary

  1. Is the stack appropriate? Yes, unambiguously. Laravel 11 + Inertia + React + PostgreSQL is lean, coherent, and right-sized. 80/100; the only waste is 5 dead npm devDependencies.
  2. Is the architecture appropriate for the current product? In shape, yes — monolith, observer cascades, cron-based async are all correct calls. In execution, it is under-enforced: authorization, transactions, type checking, and tenant scoping all rely on developers remembering to do the right thing.
  3. Is the codebase unnecessarily complex? No. It has the right number of layers and no speculative abstraction. Its complexity is accidental, not designed: duplication (3 i18n mechanisms, 6 theme lists, 4 stage maps) and two god files.
  4. Is it under-engineered anywhere? Yes — precisely at the enforcement points: a verified-middleware that never verifies, authorization that is opt-in per method, TypeScript that is never checked, multi-write paths without transactions, a tenant scope that fails open, and status strings without a controlled vocabulary.
  5. Three largest architectural risks: (1) security controls that appear present but don't fire (email verification) plus unguarded mutations and plaintext credential leakage; (2) rule duplication across PHP and JS with measured divergence — UI and backend already disagree about deadlines, stage locks, and what "in progress" is called; (3) the two god files that block team scaling and concentrate regression risk.
  6. What should NOT be changed? The monolith, the stack, the observer-cascade pattern, the queue-via-cron design, the broadcast design, the export/activity-log services, and the core test suite.
  7. What should be fixed first? The four P0 items — all are days of work, not weeks: implement MustVerifyEmail and remove the testing bypass; add role middleware and sweep unguarded endpoints; stop persisting PINs and email bodies; fix the three worker-UI crashes and switch on tsc --noEmit in CI.
  8. Would you approve continued development on this architecture? Yes — conditionally. Approve feature development to continue in parallel with a 1-2 sprint P0/P1 hardening track. Do not approve adding new dashboard features into the two god files; new work lands in extracted services/components from day one.
