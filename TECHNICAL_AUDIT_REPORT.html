Kekuatan Utama

  1. Isolasi Multi-Tenant Sangat Kuat — BelongsToTenant trait + TenantScope global scope mencegah kebocoran data antar-tenant secara arsitektural.
  2. Error Handling yang Matang — Exception handling di bootstrap/app.php mengonversi HTTP errors ke React error boundaries; worker tidak pernah melihat raw stack trace.
  3. Tech Stack Modern & Tepat — Laravel 11 + Inertia v2 + React 18 + TypeScript + Tailwind v4 + Vite 8 memberikan fondasi yang solid.
  4. Real-time Foundation Tersedia — Laravel Echo + Pusher sudah terinisialisasi dan berfungsi untuk WebSocket events.
  5. Responsive Design Solid — AppShell.tsx menyediakan layout adaptif yang mulus untuk desktop dan mobile factory floor.

Kerentanan & Bottleneck Kritis

Critical Production Secrets di Version Control ✅ RESOLVED

File deploy/.env berisi kredensial database (Neon.tech PostgreSQL), Pusher App Secret, dan SMTP password yang ter-commit ke repository git. Ini merupakan pelanggaran keamanan tingkat tertinggi.

Critical Observer Cascade Sinkronus + Inline Broadcasting ✅ RESOLVED

ShouldBroadcastNow di DataRefreshed event menjalankan HTTP call ke Pusher API di dalam request cycle user, menambah 100–300ms latency per save. Attach ke 9 model berarti bulk operations bisa trigger 20+ inline API calls.

Critical Monolithic Frontend Components ✅ RESOLVED

Owner/Dashboard.tsx berisi 6.000+ baris (416 KB). Setiap setState call me-render ulang seluruh halaman — degradasi performa signifikan terutama di perangkat factory floor.

High N+1 Query & Race Condition di Observer Chain ✅ RESOLVED

ItemProgressObserver dan DoItemObserver melakukan loop query $po->items()->get() pada setiap update. Tanpa lockForUpdate(), concurrent progress updates bisa menghasilkan kalkulasi yang salah.

Alignment Statement Codebase POgrid memiliki fondasi arsitektural yang tepat untuk real-time PO tracking (Laravel + Inertia + Pusher). Namun, implementasi broadcast yang sinkronus dan observer cascade tanpa queue bertentangan langsung dengan janji "zero data latency". Pada load tinggi (>50 concurrent users / >1000 POs per tenant), sistem akan mengalami degradasi performa signifikan. Refactoring ke asynchronous broadcasting dan service-layer architecture adalah kebutuhan mendesak sebelum scaling.

2.2 Architecture Pattern Analysis

Multi-Tenancy Implementation

High Static Properties di TenantManager

TenantManager menggunakan static::$tenantId dan static::$bypass sebagai state holder. Pada environment concurrent (Laravel Octane, queued jobs), state ini bisa "bocor" antar-request — menyebabkan query berjalan tanpa tenant scope atau dengan tenant ID yang salah.

📁 app/Services/TenantManager.php  |  app/Models/Traits/BelongsToTenant.php

Rekomendasi: Migrasi ke container-bound singleton instance atau gunakan Laravel's Context service untuk scope isolation per-request.

Observer Chain Architecture

Item::created │ ▼ ItemObserver ──→ Auto-create ItemProgress rows (per required_stages) │ ▼ ItemProgressObserver::saved │ ├── Recalculate Item progress_percent ├── Check all PO items → Update PO status │ ▼ DataSyncObserver::saved │ ▼ DataRefreshed event (ShouldBroadcastNow) │ ▼ INLINE HTTP POST → Pusher API (100–300ms blocking)
Critical Sinkronus Cascade + Inline Broadcasting ✅ RESOLVED

Seluruh observer cascade berjalan sinkronus di dalam HTTP request cycle. Satu progress update menghasilkan:

  • 3–5 cascading database saves
  • 1 external HTTP call ke Pusher API (blocking)
  • Bulk PO creation (20 items) → 20+ Pusher API calls sinkronus

📁 app/Observers/ItemProgressObserver.php  |  app/Observers/DataSyncObserver.php  |  app/Events/DataRefreshed.php

Rekomendasi: Ubah ShouldBroadcastNow menjadi ShouldBroadcast agar broadcast masuk queue. Implementasi debouncing/batching untuk DataRefreshed.

3.3 Observer Chain — Race Condition Analysis

Timeline: Dua worker mengupdate stage berbeda pada item yang sama Worker A Database Worker B │ │ │ ├── UPDATE progress ────────►│ │ │ │◄──── UPDATE progress ───┤ │ │ │ ├── saved() → read sum ─────►│ │ │ (reads OLD sum) │◄── saved() → read sum ──┤ │ │ (reads SAME old sum) │ │ │ │ ├── UPDATE items SET ───────►│ │ │ progress = calc_A │ │ │ │◄── UPDATE items SET ────┤ │ │ progress = calc_B │ │ │ │ ▲ Worker A's update is LOST
Race Condition & N+1 Risk ItemProgressObserver memanggil $item->po->items()->get() setiap kali progress di-update. PO dengan 500 items + 50 stage updates = 50× query SELECT * FROM items WHERE po_id = ?. Tanpa lockForUpdate(), concurrent updates menghasilkan last-write-wins — data progress bisa salah.

Real-time UI Synchronization

Medium Reload-on-Event Pattern — No Optimistic Updates

Pola saat ini: WebSocket event → router.reload({ preserveState: true, preserveScroll: true })

Kelebihan: Sederhana, data selalu fresh dari server.

Kekurangan: Tidak ada optimistic UI update — user menunggu full round-trip (WebSocket → server → Inertia response) untuk melihat perubahan.

Events yang di-listen: .kendala.reported, .qc.rework.logged, DataRefreshed

State Management & TypeScript Quality

High Zero Global State + Rampant any Types

State: 100% local useState + Inertia page props. Tidak ada Context, Zustand, atau Redux. Semua state terpusat di root component → extreme prop drilling → satu perubahan state me-rerender seluruh halaman.

TypeScript: Owner/Dashboard.tsx memiliki 50+ instances of : any. Tidak ada shared interfaces untuk Item, Po, Alert, event payloads. Tidak ada tsconfig.json.

i18n Implementation

Medium Per-File Translation Dictionaries

Translation dictionaries di-hardcode per-file (const translations = { en: {...}, id: {...} } di setiap page). Duplikasi massive, impossible untuk maintain secara terpusat. Harus migrasi ke react-i18next atau Inertia middleware-based translations.

4.4 Mass Assignment Risk

High Calculated Fields di $fillable — Item.php

Item.php memasukkan progress_percent, status, dan delivery_status dalam $fillable. Jika controller menggunakan $request->all(), field-field yang seharusnya hanya diubah oleh observer bisa di-spoof melalui request.

Rekomendasi: Pindahkan field kalkulasi dari $fillable — hanya observer/service yang boleh mengubah.

4.5 Data Integrity Risk

Medium Item Name Mutator Menghapus Data Asli

getItemNameAttribute() di Item.php menghapus substring seperti (cnc) via regex. Jika item bernama "Bracket (CNC)", nama asli hilang pada saat dibaca — merusak source-of-truth.

Rekomendasi: Simpan display name terpisah atau gunakan computed property yang tidak memodifikasi source data.
